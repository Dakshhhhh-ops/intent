Intent Replay — App Map

A take-home guide to where things live. Snapshot of commit a70f07e; the code may have moved on since, so search for the symbol names if a line number has drifted.

What the app does

Intent Replay reads one AI coding agent's session log (Claude Code, Codex, or the open Intent Trace format) and checks what the agent said against what the log shows it did. Each claim in the agent's closing message ("all tests pass", "fixed", "only changed X") gets a verdict with the step that proves it. Around that check, the same run becomes a replayable timeline, line-by-line blame, and a list of findings.

Parsers

src/core/parse/ turn each agent's log format into one list of steps.

Analyzer

src/core/analyze/ rebuilds files, checks claims, runs the review rules, groups chapters.

Viewer

src/ui/ is the React app: Brief, Replay, Changes, Findings.

CLI

cli/ finds local sessions, serves the viewer, prints reports, runs audit.

There is no server, database or external service: everything runs in the browser or in Node on your machine.

One action, end to end

Action: open the sample “All tests pass.” They didn't. and see the claim stamped Contradicted next to the failing test output.

Reference route: three stops

A reference route through the code for the action above. Open the project in your editor and search for each symbol.

  1. Read the log

    src/core/parse/detect.ts → parseTrace, then src/core/parse/claudeCode.ts → parseClaudeCode

    parseTrace works out which agent wrote the file and hands it to that parser. parseClaudeCode walks the log line by line and turns reads, edits, commands (with their exit codes and output) and messages into steps. This is why the replay shows step 12: Re-run the suite.

  2. Check the claim

    src/core/analyze/claims.ts → findClaimsInText, checkClaims, weakProof; helpers in src/core/analyze/commands.ts → failedAs, testSummary

    findClaimsInText spots "All tests pass." in the agent's last message. checkClaims finds the last test run before it. That run exited 0, but only because | tail hid the real exit code; failedAs sees the failures in the output, so the verdict is Contradicted. weakProof is the other side: it stops weak evidence (a scratch copy, a cut-off summary, a wrong test count) from earning a green stamp.

  3. Show it

    src/ui/Brief.tsx → Brief (the "said vs shown" block), src/ui/Evidence.tsx → maskingPipe

    Brief puts the agent's words next to what the log shows, with the seal between them. The evidence card prints exit 0 · hidden by | tail, which maskingPipe works out from the command.

To change this, start here

  • A new kind of claim (e.g. "the docs are updated"): add a pattern to PATTERNS in src/core/analyze/claims.ts, then decide its verdict in evaluate in the same file. Add a case to tests/claims.test.ts.
  • A new review rule: write a Rule in src/core/analyze/rules.ts and register it in RULES and RULE_INFO. Tests go in tests/rules.test.ts.
  • Another agent's log format: add a parser next to claudeCode.ts and a branch in parseTrace (src/core/parse/detect.ts).
  • How the run is split into chapters: chapters in src/core/analyze/chapters.ts (used by both the Brief and the report).
  • Colors and spacing of the Brief: src/ui/brief.css (start at .bv-duel); shared tokens are at the top of src/ui/styles.css.
  • A new CLI command: the switch in main in cli/main.ts; audit there is a small example.

A practice to reuse

Measure on real data, and check both kinds of answer by hand. The claim checker was first run on 86 real local sessions (intent-replay audit, in cli/main.ts). Reviewing every red verdict found ESLint warnings being read as failures; reviewing random samples of green verdicts found weak proof such as a scratch-copy test or "146 tests" backed by a run of 8. Each fix became a named test in tests/claims.test.ts (for example the block "proof, second round (from a hand review of 30 supported verdicts)").

On another project, the same move works for any tool that gives a verdict: run it on real inputs, hand-check a sample of the "yes" answers as well as the "no" answers, and turn each mistake into a test before fixing it.

Run it again

git clone https://github.com/Dakshhhhh-ops/intent && cd intent
npm install          # also builds the viewer and the CLI
npm run dev          # viewer with hot reload; open the printed localhost link
npm test             # unit tests
node dist-cli/intent-replay.mjs audit   # fact-check every local session, counts only

Or open the hosted viewer: dakshhhhh-ops.github.io/intent.

Where the rest lives

src/core/analyze/files.ts rebuilds each changed file and remembers which step wrote every line (the blame in Changes). src/core/parse/slim.ts drops bulky bookkeeping from huge logs before parsing. src/ui/parseWorker.ts parses dropped files off the main thread. scripts/import-run.ts turns a real session into a shareable sample and refuses to write one that still contains personal data.
